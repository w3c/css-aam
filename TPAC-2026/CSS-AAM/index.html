State of the spec

But first the state of the spec, what have we done so far?.

State of the spec

  • Skeleton is landed
  • display as first property
  • visibility as second property
  • Something more recent after that
  • Roadtest CSS-AAM as for building consensus
  • The first goal is to get one fundamental property landed which isn't too controversial to kick things off. We chose the display property. That's mostly done, but there are some editorial and process niggles which need to be resolved before we can land it (see agenda item 2 below).
  • Once that's merged, we want to get another fundamental property merged, probably visibility.
  • Then, we want to work on something more recent that has been implemented in browsers but is less well known, and thus where documentation is quite timely and impactful. Maybe CSS anchor positioning? Or CSS highlights?
  • It'd then be good to road test CSS-AAM as a vehicle for building consensus on a CSS item which is not yet decided across browsers.

Editing

  1. Explicitly state there’s no impact
    • display: contents
  2. Deviating from other AAMs
    1. Do we just say “not mapped”?
    2. How much can we deviate?
    3. Can we have longer form prose?
  • There are a lot of cases in CSS-AAM where we need to explicitly state that some property has no impact on the accessibility tree, but where authors might incorrectly intuit that there will be some impact.
  • display: contents is a great example. We need to explicitly state that the element should be included in the accessibility tree because it is the entire point of that property; exceptions apply. So "not mapped" seems understated/insufficient.
  • Current AAM spec language doesn't seem to really allow for that. Do we just say "not mapped" and use comments to make this clear? Or is there some other terminology we can use?
  • CSS-AAM is quite different to the other AAMs in that it doesn't just map to roles and states. It can also create accessibility nodes from pseudo-elements, impact text attributes, etc.
  • How much latitude do we have to completely deviate from the other AAMs? Is it reasonable to just have longer form prose in some sections?

Process

  1. Who should review our PRs?
    • Browser vendors?
    • Editors?
  2. What are the requirements for landing things?
    • ARIA WG Process Document requires two implementations
  3. How do we merge WPT PRs?

For example, the ARIA process requires two implementations. Initially, most of these things should hopefully already be implemented in browsers. We're just writing down what is currently unwritten. So does that mean we can just merge it once reviewed?
